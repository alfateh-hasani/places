API Documentation

Introduction

This RESTful API provides comprehensive endpoints for managing bookings, customers, apartments, and integrations with third-party services like Guesty and OwnerRez.

Base URL: /api

API Version: v1

Content-Type: application/json

All endpoints require the appSecret middleware unless otherwise specified. The API uses JSON for request and response payloads.

Response Format

All API responses follow a consistent JSON structure:

{
    "status": true|false,
    "message": "Response message",
    "data": { ... }
}

HTTP Status Codes

Code Description
200 Success - Request completed successfully
201 Created - Resource created successfully
400 Bad Request - Invalid request parameters
401 Unauthorized - Authentication required or invalid token
403 Forbidden - Insufficient permissions
404 Not Found - Resource not found
422 Unprocessable Entity - Validation errors
500 Internal Server Error - Server error occurred

Authentication

The API uses OTP (One-Time Password) based authentication. The authentication flow consists of three steps:

  1. Request OTP - Send phone number to receive OTP code
  2. Verify OTP - Verify the OTP code to receive authentication token
  3. Use Token - Include the token in subsequent API requests
Authentication Required: Most endpoints require authentication using the auth:api middleware. You must include a valid bearer token in the Authorization header for protected endpoints.

Header Format

Include the authentication token in the request headers:

Authorization: Bearer {your_access_token}
Content-Type: application/json
Accept: application/json

App Secret

All endpoints require an appSecret header or parameter. This secret is used to validate API requests and should be kept secure.

Token Expiration

Authentication tokens expire after a certain period. When a token expires, you will receive a 401 Unauthorized response. You must request a new OTP and verify it to obtain a new token.

Authentication Endpoints

These endpoints handle user authentication using OTP (One-Time Password) verification.

Request OTP

POST /api/otp/request

Request a one-time password (OTP) to be sent to the user's phone number. The OTP is typically sent via SMS and is valid for a limited time period.

Request Body Parameters

Parameter Type Required Description
phone string Yes Phone number in international format (e.g., +1234567890)

Example Request

POST /api/otp/request
Content-Type: application/json

{
    "phone": "+1234567890"
}

Example Response (200 OK)

{
    "status": true,
    "message": "OTP sent successfully",
    "data": {
        "expires_in": 300
    }
}

Verify OTP

POST /api/otp/verify

Verify the OTP code received by the user. Upon successful verification, an authentication token is returned that should be used for subsequent API requests.

Request Body Parameters

Parameter Type Required Description
phone string Yes Phone number used to request OTP
otp string Yes The OTP code received via SMS

Example Request

POST /api/otp/verify
Content-Type: application/json

{
    "phone": "+1234567890",
    "otp": "123456"
}

Example Response (200 OK)

{
    "status": true,
    "message": "OTP verified successfully",
    "data": {
        "token": "eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9...",
        "user": {
            "id": 1,
            "name": "John Doe",
            "phone": "+1234567890",
            "email": "john@example.com"
        }
    }
}

Error Responses

400 Bad Request: Invalid OTP code or expired OTP

{
    "status": false,
    "message": "Invalid or expired OTP code"
}

Add Booking

POST /api/booking/add-booking

Create a new booking for an apartment. This endpoint validates availability, calculates pricing, and creates the booking record. The booking status will be set to pending until payment is confirmed.

Request Body Parameters

Parameter Type Required Description
apartment_id integer Yes ID of the apartment to book
check_in date Yes Check-in date (format: YYYY-MM-DD)
check_out date Yes Check-out date (format: YYYY-MM-DD)
guests integer Yes Number of guests
coupon_code string No Optional coupon code for discount
services array No Array of service IDs to include

Example Request

POST /api/booking/add-booking
Authorization: Bearer {token}
Content-Type: application/json

{
    "apartment_id": 123,
    "check_in": "2024-02-01",
    "check_out": "2024-02-05",
    "guests": 2,
    "coupon_code": "SUMMER2024",
    "services": [1, 3]
}

Example Response (201 Created)

{
    "status": true,
    "message": "Booking created successfully",
    "data": {
        "id": 456,
        "booking_number": "BK-2024-001",
        "apartment_id": 123,
        "check_in": "2024-02-01",
        "check_out": "2024-02-05",
        "guests": 2,
        "total_amount": 500.00,
        "discount_amount": 50.00,
        "final_amount": 450.00,
        "status": "pending",
        "created_at": "2024-01-15T00:00:00.000000Z"
    }
}

Error Handling

The API uses standard HTTP status codes and returns error responses in a consistent JSON format.

Error Response Format

All error responses follow this structure:

{
    "status": false,
    "message": "Error message describing what went wrong",
    "errors": {
        "field_name": ["Validation error message"]
    }
}

Common Error Scenarios

Status Code Scenario Description
400 Bad Request Invalid request parameters or malformed JSON
401 Unauthorized Missing or invalid authentication token
403 Forbidden Valid token but insufficient permissions
404 Not Found Requested resource does not exist
422 Validation Error Request validation failed with field-specific errors
429 Too Many Requests Rate limit exceeded
500 Server Error Internal server error occurred

Validation Errors Example

When validation fails, the response includes field-specific error messages:

{
    "status": false,
    "message": "Validation failed",
    "errors": {
        "email": ["The email must be a valid email address."],
        "phone": ["The phone field is required."],
        "check_in": ["The check-in date must be after today."]
    }
}

Rate Limiting

The API implements rate limiting to ensure fair usage. Rate limit information is included in response headers:

  • X-RateLimit-Limit: Maximum number of requests allowed
  • X-RateLimit-Remaining: Number of requests remaining in current window
  • X-RateLimit-Reset: Timestamp when the rate limit resets

When rate limit is exceeded, a 429 status code is returned with a Retry-After header indicating when to retry.
